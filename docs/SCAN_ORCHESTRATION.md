# Phase 7 scan orchestration

This phase implements the job lifecycle with a **network-free mock provider**. ZAP, real collection/normalization, Gemini, deterministic security policy evaluation and security report generation are not connected. Mock completion means the lifecycle finished, not that an application passed a security test.

## Run

Apply migration `0005` with `make migrate`. Leave `AEGIS_SCANNER_PROVIDER=none` for the default fail-closed behavior. For local demonstrations set `AEGIS_SCANNER_PROVIDER=mock` and `AEGIS_DEMO_MODE=true` in `.env`, then recreate the API and worker with `docker compose up --build -d --wait api worker`. Mock settings are rejected in production. The test profile permits mock fixtures without demo mode, but still requires explicitly selecting the mock provider. Nothing contacts a target during a mock scan; target registration retains its Phase 6 reachability check.

The API must remain running for dispatch and reconciliation. Every API instance starts a coordinator unless `AEGIS_SCAN_COORDINATOR_ENABLED=false`; multiple instances coordinate through PostgreSQL locks. Disabling all coordinators deliberately stops progress and deadline reconciliation until one returns. Redis outages do not destroy accepted jobs or event history. API/database outages delay reconciliation; elapsed deadlines are enforced when the control plane recovers.

## HTTP contract

All scan routes take `organization_id` as a routing query parameter. It selects a tenant; it does not grant access. The authenticated principal's current organization membership and project assignment are checked on the server. Writes require the existing CSRF header/cookie and Origin defenses. No access credentials appear in URLs.

- `POST /api/v1/scans?organization_id=…`: requires `Idempotency-Key` (1–200 printable ASCII characters); returns **202** and the durable scan resource. Body: `target_id`, `target_version`, `policy_id`, `policy_version`, `secret_reference_ids`, optional `trigger` (`source: manual|ci`, `branch`, hexadecimal `commit`), `active_acknowledgement` and active-only `confirmation_token`. CI here is metadata supplied by an authenticated browser principal, not an integration-token API.
- `POST /api/v1/scans/confirmations?organization_id=…`: validates the same active-scan body, requires acknowledgment, and issues an opaque five-minute, single-use grant bound to the member and exact configuration/trigger/reference fingerprint. Creation atomically consumes the grant. Idempotent replay returns the original resource without consuming another grant. A changed request conflicts, including changed target/policy versions.
- `GET /api/v1/scans?organization_id=…`: newest 200 accessible scans; same bounded-list limitation as Phase 6. Detail: `GET /api/v1/scans/{id}?organization_id=…`.
- `POST /api/v1/scans/{id}/cancel?organization_id=…`: atomically enters cancelled and revokes the fence. Terminal scans return 409; history is never rewritten.
- `GET /api/v1/scans/{id}/events?organization_id=…`: SSE `scan` frames with integer `id`, stage, safe message code, attempt and timestamp. `Last-Event-ID` replays strictly greater sequences. Invalid or future cursors fail explicitly. `end` signals terminal history; `access_revoked` closes revoked access. Streams send heartbeats and roll over after approximately 25 seconds, allowing access-token refresh. Every database read rechecks access and releases its transaction before delivering frames.

Creation serializes on the organization lock and checks the active project/target, current authorization owner and expiration, target/policy versions, selected tenant/target-bound non-revoked credential references, organization concurrency (default 3) and rolling 24-hour quota (default 100). No credential value is loaded by the orchestrator or sent to the broker. The execution snapshot preserves policy rules and selected reference IDs; stage entry checks current configuration versions and authorization scope digest again.

## Durable control plane and isolated worker

The committed scan stage, `job_id`, fence and dispatch timestamp form a per-stage transactional outbox. The coordinator commits a job identity **before** publishing it. An interrupted/uncertain publish repeats the same identity. PostgreSQL organization/scan row locks serialize coordinators, commands, event allocation and state changes; results must match scan ID, job ID, stage and fence. Every transition increments version/fence and appends its event in the same transaction. Existing database immutable-history triggers protect events; sequence uniqueness is tenant/scan scoped.

The Celery worker remains on `worker_broker`, with no API/database network or database credentials. Its validated message has only opaque IDs, fence, stage and a demo flag. Redis admission uses a two-hour per-job deduplication key and a per-scan 25-second lease; the Celery hard execution limit is 20 seconds (soft limit 15). A duplicate job or occupied scan is ignored; Redis admission failure prevents execution. Lease release compares its owner token. Mock work is bounded to at most 10 seconds and has no external side effects. Cancellation fences off its eventual result; an already-running mock function may finish its bounded calculation. Real runner termination/egress revocation belongs to the future isolated scanner adapter and must be implemented before any real traffic is enabled.

The coordinator checks terminal state, deadline and current authorization before dispatching or accepting results. Unknown/invalid provider output fails closed. A missing/mismatched provider records `scanner_unavailable`. A result matching an old fence cannot advance the scan. Unobserved stage results expire after `AEGIS_SCAN_STAGE_TIMEOUT_SECONDS` (minimum/default 30). Only validation, preparation and downstream result-processing stages retry, at most three attempts; retries stay in the same stage and get a fresh job/fence. Spidering/passive/active execution is never blindly retried. Lost or uncertain execution fails `worker_lost`. Queue/publish retries end at the persisted policy deadline. There is no automatic creation of a replacement scan; the user must submit a new reviewed request and fresh active grant.

## Mock semantics and frontend

The deterministic `mock-v1` protocol advances the documented graph. It stores a labeled synthetic manifest plus a simulated fail evaluation/report explanation on the demo scan, **not** real artifacts, findings, PolicyEvaluation or Report records. Completeness remains partial; enrichment is mock; report status is failed because no security report exists. Effective gate is always fail, including completed mock runs and all incomplete/missing-evaluation states. `demo_not_security_evidence` identifies finished fixtures. These choices preserve Phase 7's boundary and cannot satisfy onboarding's complete-evidence requirement.

`/app/scans` shows state, mode, target/project, branch/commit, initiator, start time and duration. `/app/scans/new` reviews target, immutable policy version, trigger/active consent and final submission. The current target's unrevoked masked references are selected for the review. `/app/scans/:scanId` displays stage, stepper, elapsed time, separate completeness/component/gate status, cancellation and the sanitized terminal timeline. The fetch-based SSE client keeps access credentials in memory, refreshes expired sessions, reconnects with `Last-Event-ID`, rejects gaps and deduplicates replay by sequence. Events contain allowlisted codes only: raw target output, exceptions, URLs, credentials and response bodies never become logs.
