# Dashboard analytics and workspace UX

Phase 12 adds `/app/dashboard` and `/api/v1/analytics/dashboard`. Authentication resolves a current organization membership; owners/admins see active organization projects, while developers/viewers see only their assigned active projects. Project and target filters further restrict this scope, never grant access. Organization IDs are selectors, not authorization. All metrics, distributions, trends, risk rows and activity are calculated in one PostgreSQL statement, sharing one MVCC snapshot. No browser-side dataset aggregation or evidence download is required.

## Filters and time

The dashboard URL persists `organization`, `project`, `target`, `date_from`, `date_to`, `timezone` and risk-table `page`. The API uses `organization_id`. Organization changes clear subordinate filters; project changes clear the target. Dates are timezone-aware instants with inclusive start and exclusive end; the default is the preceding 30 days, maximum 366 days. Date inputs explicitly use midnight UTC. The display timezone is an IANA identifier, defaulting to the browser timezone; daily buckets and activity use it, including daylight-saving transitions. Invalid ranges/timezones return 422 instead of silently broadening scope.

Unless otherwise specified, scans belong to a window by creation time and findings by last observation time. Finding counts describe their **current state**, restricted to findings last observed in that window; they are not a historical reconstruction of state at the end date. Archived targets remain represented when their project is active, preserving retained evidence.

## Metric definitions

| Metric                           | Definition and exclusions                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Completed scans                  | Count of non-demo scans created in the window with both state `completed` and completeness `complete`.                                                                                                                                                                                                                                                     |
| Open findings                    | Canonical findings last observed in the window whose current state is new, recurring, reopened or changed. Accepted risk, false positive and resolved are excluded. Observed findings from partial scans remain evidence and are included.                                                                                                                 |
| New high / critical findings     | Canonical findings first observed in the window with current scanner severity high or critical, regardless of current disposition. This is not an AI severity.                                                                                                                                                                                             |
| Targets recently scanned         | Distinct targets represented by completed scans as defined above.                                                                                                                                                                                                                                                                                          |
| Policy pass rate                 | 100 × passing latest evaluations / conclusive latest evaluations. Exactly one latest retained evaluation per complete scan, ordered by creation timestamp then ID. Outcomes pass, warn and fail are conclusive. Missing/incomplete evaluations are excluded, not passing. Zero denominator produces null/“Insufficient data”.                              |
| MTTR                             | Arithmetic mean of `resolved_at - first_seen_at`, in hours, for currently resolved findings resolved in the window with nonnegative duration. Findings need not have been last observed in the window. Null if none; the UI omits the card in that case. This measures the current resolution episode from original discovery, not engineering work hours. |
| Severity distribution            | Counts of the same open canonical findings by current scanner severity. Its total equals the open-findings KPI and all pages of the risk table.                                                                                                                                                                                                            |
| CWE categories                   | Same open findings grouped by current CWE; absent values are “Unclassified”. Top 30 groups ordered by count, then label.                                                                                                                                                                                                                                   |
| OWASP categories                 | Same open findings, one distinct finding per scanner-provided OWASP category; a finding may belong to multiple categories, so totals are not additive across categories. Unmapped findings do not receive invented mappings. Top 30 groups.                                                                                                                |
| New / recurring / resolved trend | Distinct finding/scan pairs from retained finding-review observations in the selected time window, grouped by review date in the display timezone and recorded state. Only complete, completed, non-demo source scans qualify. This is observation frequency, not a daily inventory or net-new count.                                                      |
| Scan duration trend              | Mean elapsed minutes from start to finish of complete scans, grouped by finish date. Missing or negative durations are excluded explicitly.                                                                                                                                                                                                                |
| Scan completion trend            | Daily percentage of scans created that day that are now completed and complete. All non-demo scans in the selected window are in the denominator, including queued/failed/cancelled/partial/timed-out scans. This is not a success rate over only terminal scans.                                                                                          |
| Project / target risk            | Current open finding and high/critical counts for each permitted target, using the same finding window as the KPI and distributions. This is a count table, not a fabricated numerical risk score. Descending high/critical, then open count, then target ID; 50 rows/page.                                                                                |
| Recent scan activity             | Latest 15 non-demo scans created in the window, showing state and completeness separately.                                                                                                                                                                                                                                                                 |
| Failed scans action              | Count of failed or timed-out scans in the selected creation window.                                                                                                                                                                                                                                                                                        |
| Overdue targets action           | Targets without a non-demo complete scan finishing during the 30 days preceding the selected end. This explicit 30-day convention is not a user-defined SLA.                                                                                                                                                                                               |
| Expired exceptions action        | Distinct finding IDs with expired exceptions in the latest active gate for the selected projects/targets. Historical deactivated gate versions are excluded. Expiry is evaluated at the selected end.                                                                                                                                                      |
| Unresolved high findings action  | High/critical subset of the open-findings population.                                                                                                                                                                                                                                                                                                      |

Adding a review note preserves the resolution timestamp and therefore does not change MTTR.

The action list shows up to ten direct record links per category in addition to total counts.

The dashboard reports the number of incomplete/unfinished scans excluded from completion-dependent metrics, complete scans with invalid duration, and complete scans without a conclusive gate. Demo scans are excluded from scan metrics. A known empty population is zero; an undefined ratio/mean is insufficient data. Finding records do not contain an `is_demo` flag; canonical finding counts use their retained evidence regardless of whether earlier synthetic ingestion created them. Use separate demo organizations rather than mixing demo and production evidence.

## Workspace and exports

The compact sidebar exposes Getting Started, Dashboard, Projects, Targets, Scans, Findings, Reports, Integrations, API Keys, Team, Audit Log and Settings. Policy gates and scan policies remain directly accessible. Onboarding retains native keyboard-accessible accordions and server-calculated progress. Existing project/target configuration, scanning, finding review and policy commands retain their server authorization and CSRF defenses. Team and settings reuse the working organization-management APIs. Browser back/forward honors organization selectors in the URL.

`GET /api/v1/workspace/{kind}` lists 50 safe metadata rows per page for reports, integrations, API keys or audit log. Reports are project-scoped. Administrative registries require owner/admin. API key hashes, integration credential references, report object keys and audit payloads are never returned. Integration deactivation and API-key revocation require CSRF and append an audit record. These registry pages expose retained records; provider installation, usable API-key issuance/authentication, report generation and verified artifact downloads are not introduced by Phase 12.

Dashboard risk, findings and registry CSV exports include only the currently loaded authorized page. They exclude evidence, routes, request/response contents, tokens, credential references and artifact keys. CSV quotes embedded punctuation and neutralizes spreadsheet-formula prefixes. Export filenames are generic and do not disclose organization names.

The dashboard has loading skeletons, retryable errors, explicit permission errors, empty states and a stale indicator after five minutes. A filter change clears the previous dataset so it cannot masquerade as results for the new scope. Registries have loading, empty, retry and permission states. Configuration lists and detail pages now retain accessible headings and provide loading skeletons/retry controls; team loading and retry are explicit. Native tables use header scopes, focusable scroll regions and links/buttons reachable by keyboard; the existing drawer supplies focus trapping/restoration. Responsive dashboard grids collapse for mobile. No animation is required to understand results.

## Verification boundary

See [Phase 12 test report](PHASE12_TEST_REPORT.md) for actual checks. Browser HTTP fixtures are visibly synthetic and exist only in tests. Real PostgreSQL tests validate SQL aggregation, permission boundaries, excluded scans, undefined means/rates, filter consistency, latest-evaluation selection and metadata redaction. Browser fixtures do not constitute live authenticated browser-to-database certification. Large-production-dataset throughput and cross-browser certification remain unmeasured.
