# Phase 4 persistence implementation

The executable catalog is [generated from SQLAlchemy](../generated/database-schema.md); revisions `0001` and `0002` are frozen, self-contained Alembic revisions. Neither imports current models. PostgreSQL 17 and existing locked SQLAlchemy/Alembic/asyncpg versions are reused. No dependencies changed.

## Ownership and deletion

User and RefreshSession are global identity records. Organization is the tenant root. Every other table has non-null organization_id and a unique organization/id key. Composite foreign keys bind parent records to that organization. Project assignments reference OrganizationMember, so an arbitrary global user cannot be assigned directly. Occurrences additionally bind the finding and scan to the same target and the artifact to that scan; report evaluations belong to the report's scan. Refresh replacement links stay within a user and session family.

Parent deletes use RESTRICT for retained domain/evidence/history records. Project/member assignment rows CASCADE with their project/member; refresh sessions CASCADE with their user, with deferred same-family replacement constraints. Retention must explicitly delete children before parents. No automatic purge service or soft-delete flag is introduced. Recoverable resources use active/deactivated states; sessions, keys and secret references use revocation timestamps; artifact expiry/purge metadata preserves provenance. Organizations remain globally unique by slug, users by normalized email, token/key hashes globally unique, and provider installation IDs globally bound to one organization. These deliberate global trust-boundary constraints supplement tenant-scoped uniqueness.

UUID defaults work through both ORM and PostgreSQL. TIMESTAMPTZ stores instants; the session factory sets UTC and public schemas normalize timestamps to UTC ISO-8601. Server triggers preserve created_at and update updated_at for SQL and ORM writes. IDs and tenant ownership cannot be rewritten. Policies, events, occurrences, analysis attempts, evaluations and audits reject UPDATE in PostgreSQL. Retention DELETE remains possible for an appropriately privileged future purge process; this phase does not claim a restricted production database role or RLS deployment.

## Domain boundaries

Policies have immutable name/version identities, relational thresholds/limits and versioned rules snapshots. Targets and scans separate configuration from authorization metadata; scans retain versioned redacted snapshots, authorization actor/expiry/scope and an active-confirmation digest whose uniqueness prevents reuse within the tenant. A failed/cancelled/timed-out scan cannot retain complete/unknown completeness. A passing evaluation requires complete evidence/enrichment and an appropriate downstream state snapshot. Revision 0002 additionally locks and checks the referenced scan at insertion, rejecting contradictory snapshots even when their own fields appear complete. Earlier evaluation rows remain immutable history; future live gate selection must still consider the current scan and deterministic policy. These checks are necessary consistency guards; actual ownership verification, one-use expiring grants, scanner transitions and deterministic policy evaluation are future services. No scan endpoint is exposed.

Restricted artifacts contain opaque encrypted-object/key references and hashes, never plaintext response bodies. Canonical findings, occurrences, external advisory AI output and deterministic evaluations occupy separate tables. AI output is versioned external JSON and always advisory. JSONB is limited to config/authorization/rules snapshots and external AI output. Lists of scalar scopes/reason codes use typed PostgreSQL arrays. Project ownership for scans/findings is derived through Target, avoiding a second mutable project pointer. API keys and notification destinations each bind to one project (destinations may be organization-wide); multi-project grants need a future normalized association migration, never unchecked UUID arrays.

## Repository and transaction contract

`db.session.database(settings)` returns an async engine/session factory with hidden SQL parameters, UTC sessions and explicit transaction ownership. Use `async with sessions.begin() as session`. Construct `TenantScope` only from a verified server identity or internal job authorization. Pass it to `Repository`, `TimelineRepository`, `TargetRepository` and `CommandService`. There is no HTTP tenant-scope dependency until authentication is implemented. A scope does not prove membership, role or project access; those checks must precede repository use in the owning phase. Raw sessions remain privileged infrastructure, not an authorization API.

`get` and target compare-and-swap writes return identical 404 errors for missing/foreign IDs. `add` rejects foreign ownership. Target deactivation increments a required version atomically, invalidates authorization and returns 412 for stale versions. Policy edits create a new immutable version; overwriting a policy is prohibited.

`CommandService.execute` requires an explicit transaction and a server-owned method/route/resource operation string. Use it for future scan creation, report generation and verified webhook actions. Keys bind organization + verified principal + operation + SHA-256 key hash. Canonical payload digests detect conflicting retries. PostgreSQL INSERT ON CONFLICT plus row locking serializes races; the command callback and durable receipt commit together. An internal savepoint rolls back both if a callback fails, even if the caller catches the exception and commits unrelated work. Locked receipts refresh the session identity map, and expiry is compared with database time after acquiring the lock. The callback must neither commit nor perform external effects. Persist future outbox rows there instead. Retries replay only resource UUID/status, never secret-bearing response bodies. TTL is 24 hours; expired rows may be reused under lock. Durable future webhook event IDs still need their own receipt constraint beyond TTL. The polymorphic principal/resource IDs are opaque references, not authorization or foreign keys; verified integration/member dispatch must validate them.

## API conventions and documentation

Business routes will use `/api/v1`; health routes retain their existing unversioned contract. Only health endpoints are currently executable. Development/test docs and OpenAPI live under `/api/v1`, disabled in production. All API exceptions, HTTP errors, request validation errors and unexpected failures use `{error: {code, message, details, request_id}}`, with server-owned request IDs and no-store headers. Error handlers omit caller values, validation locations/context, arbitrary exception details and dependency headers. Readiness retains its established safe status response for 503.

FindingQuery accepts `target_id`, `severity`, `state`, `cwe`; EventQuery requires `scan_id`. Both accept `limit` (25 default, 100 maximum), `cursor`, and `order=created_at|-created_at`. Extra fields/order expressions are rejected. Timeline queries use `(created_at,id)` as the stable key, return `limit+1` internally and produce next_cursor/has_more. Signed cursors bind tenant, resource, all filters, limit and order. Supply a managed random signing key of at least 32 bytes when exposing routes; test keys are synthetic and no runtime key is configured prematurely. ETags are quoted PostgreSQL INTEGER versions from 1 through 2147483647; missing If-Match yields 428 and malformed/weak/wildcard tags yield 400.

`make schema-docs` regenerates current-route OpenAPI, separate reusable convention JSON schemas and the database catalog. `make schema-check` runs in the normal quality gate. Planned endpoint tables in API_CONTRACT remain a roadmap, not implemented routes. ORM records and restricted fields are never automatically turned into public Pydantic schemas.

## Verification and deferred work

Factories create reserved `.invalid` targets and explicitly synthetic records, disabled destinations/integrations and no passwords or real secret values. Integration fixtures provision two organizations and a disposable database; no user database is downgraded. Tests cover migration upgrade/downgrade/re-upgrade and metadata drift, uniqueness, delete behavior, cross-tenant repository access/writes, graph identity immutability, timestamp triggers, enum/UTC serialization, cursor ties/tampering, CAS, command conflicts/expiry/concurrency and rollback. API boundary tests cover sanitized 404/403/422/500 responses and request correlation.

Authentication, role/project authorization, RLS/runtime database grants, target verification, actual secret encryption/storage, scanner execution, policy decisions, AI validation/enrichment, report generation, delivery, webhook verification/outbox and retention remain unimplemented. The schema alone must not be presented as any of these capabilities. Stop after Phase 4; the next prerequisite is authentication under a new explicit phase prompt.
